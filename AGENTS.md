When adding SSH to a Docker stack, use container port 22 and the next available host port in the 22xx range. Use `/home/irae/.ssh/authorized_keys` as the lab SSH public-key allowlist. For shell SSH, reuse `local-llm-sandboxed/sshd-run.sh` and copy that file at image build time. For an application-managed Git-only SSH endpoint, sync the keys into the intended application account using its supported API; do not add shell access or rebuild an official image just to distribute keys. See [README.md](README.md) for current assignments, rebuild guidance, and the container-user/access model. Agents and coding sessions must use an existing unprivileged application account. Root may run initialization and sshd, but configure SSH for key-only application-user access with root login disabled. Plain Docker exec inherits the container's default user; document explicit `--user` and `HOME` arguments, and show a maintenance-only warning in interactive root Bash shells. Preserve authoritative application configuration/environment and audit user work before changing ownership or recreating containers.

The operator accepts Docker management by existing authorized users as part of the lab threat model, including its root-equivalent implications. Treat that as established: do not repeat warnings about it, add restrictions merely to mitigate it, or prevent an authorized container operator from deploying. Agents still must not use Docker to bypass host permissions or grant Docker access to users that do not already have it.

Use the instance-level Forgejo runner for Actions across repositories. Do not mount the host Docker socket into the runner or workflow containers. Automated host deployments go through `host/forgejo-deploy`: add one application at a time with a separate API key mapped to one allowlisted deployment command.

Do not write fixed IP addresses, disk UUIDs, or other values that change into repo files. Use hostnames, CIDRs, or placeholders such as `<data-disk-uuid>`. See the host access rule in [README.md](README.md).

Expose new web services through Tailscale Serve over HTTPS, using the loopback port as the Serve port when it is free, for example `tailscale serve --bg --https=5007 http://127.0.0.1:5007`. For container ports exposed through Tailscale Serve, publish only on host loopback (`127.0.0.1`), not on the Tailscale IP or a wildcard address. Configure persistent forwarding with `tailscale serve --bg` and let Serve handle tailnet access. This lets Docker restart containers at boot without waiting for Tailscale to assign an address.

Agents cannot open a browser for the user from `sheeta`. When the user asks to open a service, give the full Tailscale Serve URL, including path, for example `https://<sheeta-tailnet-name>:5007/inbox`. Get the hostname from `tailscale status --json | jq -er '.Self.DNSName | rtrimstr(".")'`.
